# Contributing to Lowground

Thanks for contributing to Lowground.

The project is still in its foundation and browser-POC phase. Small, focused contributions are especially useful.

## Before opening an issue

- Search existing issues and documentation first.
- For product questions, explain the user problem and the musical scenario.
- For network or audio reports, include browser, operating system, connection type, devices and observed diagnostics when possible.
- Never include credentials, private room links or personal data in a public issue.

## Development workflow

1. Create a focused branch from `main`.
2. Read the relevant product and architecture documentation.
3. Keep changes small and explain important trade-offs.
4. Update documentation or memory records when a decision changes.
5. Open a pull request with a clear summary and test notes.

## Commit messages

Use concise, imperative commit messages. Prefer a simple conventional prefix when useful:

- `feat:` for user-facing functionality;
- `fix:` for corrections;
- `docs:` for documentation;
- `test:` for tests;
- `chore:` for maintenance.

## Pull requests

A pull request should describe:

- what changed;
- why it changed;
- how it was tested;
- known limitations;
- any follow-up work.

Audio and network behavior must be tested under the documented device assumptions whenever possible.
